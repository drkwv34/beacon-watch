# OpenSpec — beacon-watch

This repo uses the [Fission-AI OpenSpec](https://github.com/Fission-AI/OpenSpec) framework (`@fission-ai/openspec`), not a hand-rolled Markdown workflow.

**Product behavior changes start as an OpenSpec change** (proposal + spec deltas + design + tasks), then implementation via Cursor skills or the CLI.

## Layout

```
openspec/
  config.yaml       schema, project context, artifact rules (read by the CLI)
  project.md        capability map and extended product context
  README.md         this file
  specs/            shipped truth — one folder per capability (`<capability>/spec.md`)
  changes/          active proposals (`<change-id>/`)
    archive/        merged changes (`YYYY-MM-DD-<change-id>/`)
```

Cursor wiring (committed, generated by `openspec init` / `openspec update`):

- `.cursor/skills/openspec-*` — agent skills (`openspec-propose`, `openspec-apply-change`, …)
- `.cursor/commands/opsx-*` — slash commands (`/opsx-propose`, `/opsx-apply`, `/opsx-archive`, …)

## CLI setup

Node ≥ 20.19:

```bash
npm install -g @fission-ai/openspec@latest
export PATH="$(npm prefix -g)/bin:$PATH"
openspec --version
```

Refresh skills/commands after upgrading the package:

```bash
openspec update --force
```

## Day-to-day workflow

| Step | Cursor | CLI |
| --- | --- | --- |
| Explore ideas | `/opsx-explore` | `openspec list`, `openspec show` |
| Propose a change | `/opsx-propose <kebab-name or description>` | `openspec new change "<name>"` then fill artifacts via `openspec instructions` |
| Check progress | — | `openspec status --change "<name>"` |
| Implement | `/opsx-apply` (ticks `tasks.md`) | follow `openspec instructions apply --change "<name>"` |
| Validate | — | `openspec validate <change-id> --strict` or `openspec validate --all` |
| Archive after merge | `/opsx-archive` | `openspec archive <change-id> --yes` |

Typical loop:

1. **Propose** — `/opsx-propose add-target-crud` creates `openspec/changes/add-target-crud/` with `proposal.md`, `design.md`, `tasks.md`, and `specs/<capability>/spec.md` deltas.
2. **Approve** — solo repo: set approval in `proposal.md` (status + approver/date). That is the gate before feature implementation.
3. **Apply** — `/opsx-apply` on a feature branch; reference the change id in the PR.
4. **Archive** — after merge, `/opsx-archive` folds deltas into `openspec/specs/` and moves the folder to `changes/archive/`.

Legacy hand template: `changes/_template/` remains as a reference; prefer `/opsx-propose` or `openspec new change` for new work.

## What needs a change proposal

| Needs a proposal | Does not |
| --- | --- |
| New or changed endpoint, schema, or job behavior | Tooling, CI, lint, dependency bumps |
| Probe policy, cache keys/TTLs, rate limits | Docs-only or copy fixes |
| Incident state machine changes | Refactors with no observable behavior change |

The Day 1 scaffold was tooling-only (no proposal). Day 2 (auth and targets) is the first product change that should go through OpenSpec.

## Validation

```bash
openspec validate --all
openspec validate <change-id> --strict
```

Fix structure and schema issues only in the adoption PR; do not implement product features under `openspec/` unless that is the assigned change.
